本記事では、UEの起動からネットワークにつながるまでの後半部分をまとめています。  
Part4では、アタッチ手続きのうちMNOが担当する部分（認証・位置登録・ベアラ確立の指示）を見てきました。  
Part5では、その続きとして、SGWからPGWに話が渡った後の流れを見ていきます。

環境によって実装形態は異なるのですが、大まかな流れとして理解していただけると嬉しいです。

## アタッチ手続きの流れ（後編）

Part4の最後、MMEからSGWへ、Create Session Requestを送っていました。  
この指示は、SGWを経由してPGWまで届けられます。

ここから先は、PGWが中心となって処理が進んでいきます。

![アタッチ接続後編 シーケンス図](/images/blog/epc-5-2.png)

### 1. PGWがCreate Session Requestを受け取る

SGWは、MMEから受け取った指示をもとに、PGWに対して **Create Session Request** を送ります。  
この中には、UEが接続したいAPN（接続先ネットワークの識別子）などの情報が含まれています。

### 2. PGWがPCRFにポリシーを問い合わせる

PGWは、受け取ったAPNの情報をもとに、PCRFへ **CCR-I（Credit Control Request - Initial）** というメッセージを送ります。  
これは、このUEにどのようなポリシー（QoSや通信条件）を適用すべきかを、問い合わせるメッセージです。  
このやり取りは **Gx** というインタフェース上で行われます。

CCR-Iを受け取ったPCRFは、DBなどからポリシー情報を取得し、 **CCA-I（Credit Control Answer - Initial）** というメッセージで応答します。
その中に **PCC（Policy and Charging Control）ルール** と呼ばれる条件が含まれています。  
PGWはこのルールを、これから作るベアラに適用します。

### 3. PGWがOCSに課金情報を確認する

ポリシーの確認と合わせて、PGWはOCSにも同様の形で問い合わせを行います。  
使われるメッセージ名はPCRFとのやりとりと同じ **CCR-I/CCA-I** ですが、こちらは **Gy** というインタフェース上でのやり取りになります。

特にプリペイド型のプランなど、リアルタイムでの課金管理が必要な場合、ここで残高や利用可能量の確認が行われます。

### 4. PGWがCreate Session Responseを返す

ポリシーと課金の確認が済むと、PGWはUEに対してIPアドレスを割り当てます。  
このIPアドレスが、UEが実際にインターネット上でデータをやり取りするためのアドレスになります。

PGWはSGWに対して **Create Session Response** を返します。  
この中に、割り当てたIPアドレスが含んでいます。

このレスポンスは、SGW→MMEの経路を通って伝えられます。  

### 5. MMEがUEにAttach Acceptを届ける

MMEは、SGWから受け取ったCreate Session Responseの内容をもとに、 **Attach Accept** という、UEへの新しい応答メッセージを組み立てます。

このAttach Acceptは、MME→eNB→UEという経路で届けられ、UEがこれを受け取ることで、アタッチ手続きが完了します。

ここまで完了すると、UEは晴れて通信可能な状態になります。

## 補足：RADIUSによる認証について

Part4では、MMEとHSSの間で行われる、契約者としての正当性を確認する認証（AIR/AIA）を紹介しました。

実務では、これとは別に、PGWが接続先のAPN（例えば企業向けネットワークなど）ごとに設置された **AAAサーバ** に対して、 **RADIUS** を使って追加の認証・認可を行うケースもよくあります。  
この場合、 **Access-Request** というメッセージがPGWからAAAサーバへ送られ、AAAサーバは **Access-Accept** （拒否の場合はAccess-Reject）で応答します。

MVNOでも認証したいという場合にこの認証が発生します。

3GPPの標準的な認証（HSSとのやり取り）とは別レイヤーの話として押さえておくと、実際の構成図やドキュメントを見たときに迷いにくくなると思います。

## まとめ

Part5では、SGWからPGWに話が渡った後の流れを見てきました。

- PGWは、SGWから受け取ったCreate Session Requestをもとに処理を開始する
- **PCRF** にポリシーを、 **OCS** に課金情報を確認する
- 確認が終わった後で、UEに **IPアドレス** が割り当てられ、Create Session Responseで返される
- MMEはこの情報をもとに **Attach Accept** を組み立て、eNB経由でUEに届ける（ここでアタッチ手続きが完了する）
- 実務では、これとは別にPGWとAAAサーバ間で **RADIUS** による追加の認証が行われることもある

Part4とPart5で、アタッチ手続きの一連の流れ（UEの接続要求から、IPアドレス払い出しまで）をひと通り追うことができました。

Part6では、ポリシーや課金情報のやり取り（CCR/CCA）について深掘りしてみようと思います。
